### 2.2 新功能（本轮重点）

**① 破坏性操作审批门禁**（归档里点名要的 tool approval）

- `drop_task` 默认**不再直接执行**：Agent 与 MCP 只登记一条待确认项，并回复「需要你确认…待确认编号 xxx」。
- 批准/取消的入口：**界面面板**（`#approvalsPanel`，每行「批准 / 取消」）、
  **CLI**（`momentum-agent approvals` / `approve <id>` / `reject <id>`）、
  **API**（`GET /api/approvals`、`POST /api/approvals/approve|reject`）。
- 待确认项存在 `user_memory.pending_approvals`，**重启不丢**；批准或取消都会消费掉同一条（**不会执行两次**）；
  同工具同参数重复请求复用同一条；按用户隔离。
- 受保护工具用 `MOMENTUM_APPROVAL_REQUIRED_TOOLS` 配置（默认 `drop_task`，`none` 关闭）。
- 核心文件：`src/momentum_agent/approvals.py`、`agents/tools/task_tools.py`（门禁拦截点）、
  `web/handlers.py`、`web/server.py`、`cli.py`、`static/js/approvals.mjs`。

**为什么做在应用层而不是用 SDK 的 `needs_approval`**：SDK 的中断恢复要贯穿流式协议的 RunState
管理与前端状态机，改动面大且容易做成半成品；应用层门禁能立刻交付同样的安全价值，
而且待确认记录本身就是可恢复状态。

**② 对话历史落库（重启/多 worker 不丢）**

- 历史写入 `user_memory.chat_history`（内存字典退化为热缓存），缓存未命中时从 store 读回；
  仍按 `MAX_HISTORY_ITEMS` 截断；损坏数据安全降级；写入失败只告警。
- 出口：`GET /api/chat/history`（只返回 user/assistant 纯文本轮次）、`momentum-agent history`、
  **界面刷新后自动回填**（`chat.js: loadChatHistory()`）。
- 顺带修掉一个真实缺口：**本地模式（未配置模型）的问答原先根本不进历史**，
  所以「历史落库」只在模型路径生效；现已两条本地分支都记录。

**③ 流式生成可以「停止」**（归档取消/中断项里客户端可交付的部分）

- 生成期间出现「停止」按钮，中断后气泡标记「（已停止生成）」、按钮隐藏、输入恢复，可立刻再发。
- 服务端不改：客户端断开即结束该轮；**已执行的工具副作用不回滚**，与既有 fail-closed 语义一致。

**④ CI 从「建议性」升级为「硬门槛」**

- `browser` 去掉 `continue-on-error`；`deploy` 的 `needs` = `[test, browser, mysql-integration]`。
- 也就是说：UI 或数据库回归**会挡住部署**。这一点在本轮立刻生效过两次（见 §5）。

## 4. 关键决策与理由（避免下次推翻重来）

1. **审批门禁放在应用层**，不用 SDK `needs_approval`（理由见 §2.2①）。
2. **历史落库用 `user_memory`**，不引入新表：两个后端通用、天然按用户隔离、备份链路已覆盖。
3. **本地模式的问答也进历史**：否则「历史落库」只有一半生效，界面刷新看不到本地对话。
4. **停止生成是客户端行为**：已执行的工具不回滚，界面明确写「已停止生成」，不假装什么都没发生。
5. **CI 硬门槛**：宁可挡住部署也不让回归上线；放宽方式写在 workflow 注释和 README 里。
6. **新浏览器用例必须先本地连跑 2–3 次**再接入 CI（本轮吃过亏，见 §5）。

## 5. 本轮踩过的坑（下次别重复）

1. **子代理在这套环境里不可用**：按用户要求开了 8 个 `spawn_teammate`，**全部在开始后挂掉**（传输故障，
   无一产出文件）；此前还有 8 次同类失败。结论：**别再用子代理**，改为「一个程序里并行做多件事」。
2. **硬门槛立刻抓到了两个问题**（这是它的价值，不是麻烦）：
   - `a47110e`：新加的对话历史浏览器用例在 Linux 上失败 → `deploy: skipped`。根因是**等待条件错了**
     （气泡先插入「…」占位，「气泡数 ≥ 2」不代表这一轮结束，更不代表历史已落库）。
   - 修的时候又发现选择器 `#chatForm button` 会命中新增的隐藏「停止」按钮 → 已统一改为
     `#chatForm button[type=submit]`。
3. **我犯的错，记下来**：`b1fd4f2` 那次本地已经跑出「236 过 / 1 失败」，我没查就推了。
   真相是 `stats.js`/`tasks.js` 模块初始化时有异步刷新，Node 里没有 `localStorage`/`fetch`/`window`，
   测试结束后抛 `unhandledRejection`，`node --test` 把**整个文件**判失败。
   **教训：看到失败先定位再推，别指望 CI 告诉你。**
4. **`chat.js` 没有 import `requestJson`**（它用原生 fetch）：我一开始误用，异常被 catch 吞掉，
   表现为历史**静默不回填**。定位手法值得复用：先 HTTP 探针确认后端有数据，再给 `initChat` 传**哨兵元素**
   看模块函数到底渲染没渲染。
5. **`String.replace` 只替换第一处**：批量改调用点时踩过，改用 `split().join()`。
6. **stub provider 需要「逐片延迟」**才能制造真实的「正在生成」窗口（`tests/stub_provider.py` 的 `delay`）。
